## Findings

1. **`board_smoke.py`: the install phase runs before the one-process check** (`board_smoke.py:204-208`).
   - `run()` calls `install()` (`install.sh` with LOAD=0) before `preflight()`'s `uptime` and `pgrep -af fpga/kv260/host/`.
   - `install.sh` then runs its ssh and rsync commands on the Kria while a board tool might still be running:
     - `rsync --delete` into `~/protoemu3c/{tools,firmware,fpga/kv260/host}`;
     - `sudo cp` over `/lib/firmware/xilinx/protoemu3c/`.
   - It never loads anything, and the one-process check still runs before any xmutil command. But with the default phases, the "one process at a time" check does not cover the first board commands.
   - The stand-in tests don't cover this order. `test_install_never_loads` checks install's environment, not that it comes after the preflight.
   - Fix: run `uptime` and the `pgrep` check before `install()` (keep listapps after it), and assert that order in a test.
2. **The documented 2-core builds now make 3-core bitstreams** (`fpga/kv260/README.md:46`, `:128-132`; `docs/hardware-day.md:112`).
   - `build.sh`'s default is now `project.v`'s 3 cores. So `fpga/kv260/build.sh && install.sh` (APP=protoemu) and `build.sh 25 && APP=protoemu48 install.sh` now build 3-core bitstreams, which `app_build.py` then refuses: "protoemu48 holds a 2-core clk_div 25 build; this one is 3 cores". The same goes for hardware-day's `PMOD_DRIVE=12 fpga/kv260/build.sh 24` for a protoemu app.
   - The refusal is safe, but claim 2's "`build.sh 25` and `PMOD_DRIVE=12 build.sh 24` keep working" is true only of the argument parsing. The documented commands need `--cores 2`.
3. **Rebuild against the committed 3-core reports: met both times, but not within tens of ps, and utilization not exact.** The asked check expected both. The cause is that the bitstream's identity is a design input.
   - `build_id.vh` puts `BUILD_HEAD_REV` (`38cf46e` for the builder, `b3a019a` for me) and `BUILD_TIME` into `pe_lab`'s readback constants (`pe_lab.v:89-126`). The digest covers the staged RTL, not that header.
   - Post-synthesis, the two runs differ by 87 LUTs (13,691 against 13,604, mine against the builder's, read-only on runner1). Registers (7,221) and BRAM (4 + 3) are equal.
   - Post-route, `u_lab` has +88 LUTs (1,231 against 1,143) and `u_pe` +4 (9,809 against 9,805). The total is 13,240 against 13,147.
   - FFs are exact: 7,093 in all, 3,584 in `u_pe`. BRAM is 4 RAMB36 + 3 RAMB18, the same.
   - So a different netlist was placed. Slacks then move by hundreds of ps, as the builder's own caveat says. Per domain (WNS / WHS, mine against committed):

     | domain | WNS mine | WNS committed | WHS mine | WHS committed |

   - In my build the tightest path is the protoemu→SPI-device crossing; in the builder's it is SPI device→MISO. Both are on the 2.5 ns crossings and positive in both builds. With one placement per build, that margin is what the evidence shows, not a guarantee for the next build.
